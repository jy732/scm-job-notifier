SCM Job Notifier — Technical Design

Automated monitor for entry-level & internship Supply Chain Management roles in California
Status: Draft Author: jy732@cornell.edu Date: 2026-08-09 Mirrors: swe-job-notifier
This service is a structural clone of swe-job-notifier: identical Spring Boot 4 / Java 17 / H2 / Playwright / Gemini stack, identical package layout, identical scheduling and observability. Only three axes change, and they are the subject of this document:
  1. Classification target — SWE level (L3 / L4) → SCM track (ENTRY_LEVEL / INTERNSHIP / UNSURE)
  2. Location filter — United States → California only
  3. Relevance filter — software-engineering titles → supply-chain titles
One structural change also falls out of the target axis: SWE's two per-track alert emails become a single alert email to one recipient list, with a Type column (Decision D1). Everything else — the two-phase scrape, in-memory dedup, three-stage classifier, retry/fallback, batch persistence, 5-minute scan cadence, daily summary, 90-day cleanup, Actuator metrics — is carried over unchanged.

1. Goals & Non-Goals

Goals

  • Detect newly-posted entry-level and internship SCM roles located in California within ~15 minutes of publication.
  • Route each detected role to the correct recipient list by track (entry vs. intern).
  • Reuse the proven swe-job-notifier architecture verbatim to minimize new code and operational surprises.
  • Run cleanly alongside swe-job-notifier on the same machine (separate port 8081, separate H2 file).

Non-Goals

  • Mid-level / senior / management SCM roles (classified as OTHER, stored, not notified).
  • Roles outside California (filtered out before classification).
  • Non-SCM roles (SWE, sales, finance, etc. — filtered out before classification).
  • A UI. Debug endpoints only, same as the SWE app.

2. Architecture Overview

A single Spring Boot process runs four scheduled jobs against a file-based H2 database. Scrapers pull postings from ATS JSON APIs (fast) and Playwright-driven SPA career pages (slower, browser-based). A three-stage classifier assigns each unseen posting a track. An independent scanner emails unnotified postings to the matching recipient list.

5. Pre-Filters — the three changed axes

Implemented in JobTitleFilter, run in this order. Any posting that fails a gate is silently dropped.

5.1 Freshness — unchanged

Reject postings older than 30 days by postedDate; postings with no date pass through.

5.2 Exclude keywords — changed

Drop titles that indicate seniority above entry level. Critical difference from SWE: the SWE app excludes intern; here internships are a target, so intern is removed from the exclude list.

SWE excludesSCM excludes
Senioritysenior, sr., staff, principal, lead, manager, director, VP, PhDsenior, sr., staff, principal, lead, manager, director, VP, head of, chief, supervisor
Internsintern (excluded)intern — allowed
Domainfrontend, mobile, iOS, Android, embedded, security(n/a — SCM relevance handled by 5.4)

5.3 Location — changed: US → California

Replaces isValidUsLocation with isCaliforniaLocation. Keep a posting if its location matches any of:

  • Explicit state token: CA, California
  • Known CA cities/metros: San Francisco, San Jose, Oakland, Fremont, Sunnyvale, Santa Clara, Mountain View, Palo Alto, Cupertino, Milpitas, Pleasanton, San Mateo, Redwood City, Los Angeles, Long Beach, Irvine, Anaheim, Santa Ana, El Segundo, Torrance, City of Industry, Ontario, San Diego, Carlsbad, Sacramento, Fresno, Riverside, San Bernardino, Santa Barbara, Bakersfield, …
  • Remote handling — see Open Decision D2

Reject known non-CA US states and all non-US patterns (the SWE non-US reject list is reused as-is, extended to reject other US states).

City-name matching needs care: "Ontario" is both a CA city and a Canadian province; "San Jose" also exists in Costa Rica. The filter should require a CA context token (, CA / California) when a city name is ambiguous, mirroring how the SWE filter disambiguates.

5.4 SCM relevance — changed: SWE → SCM

Replaces isSweRelevant with isScmRelevant. Require the title to match at least one supply-chain keyword:

supply chain, logistics, procurement, sourcing, purchasing, buyer,
operations (ops), planning, demand planning, supply planning, S&OP,
inventory, materials, warehouse, fulfillment, distribution,
transportation, category management, commodity, vendor management,
replenishment, production planning, MRP, ERP, import/export, customs,
supplier quality, order management, 3PL, freight

This gate is what removes SWE, sales, marketing, finance, and HR roles that survived the other filters.

6. Classification Pipeline (3 stages)

Structure is identical to SWE's ClassificationPipeline: three stages, each consuming only what the previous couldn't classify. Only the label set and the rules that emit those labels change.

ENTRY_LEVEL full-time entry role   INTERNSHIP intern / co-op   UNSURE can't confidently separate entry vs intern   OTHER stored, not notified

All three of ENTRY_LEVEL, INTERNSHIP, and UNSURE are emailed — they land in a single alert email as rows in one table, with a Type column carrying the label (see §7). Only OTHER is stored-but-silent. This is the key departure from SWE, whose L3/L4 split into two separate recipient lists.

SWE label→ SCM labelEmailed?

L3 (new-grad, secondary)INTERNSHIPyes — Type = INTERNSHIP
L3_OR_L4UNSUREyes — Type = UNSURE
OTHEROTHERno

Stage 1 — Title rules (JobTitleFilter.autoClassifyLevel) — zero cost

Patterns below are derived from real 2026 SCM postings (see Appendix A for the source taxonomy). The defining difference from SWE: an Engineer II title is its own level, but a bare Supply Chain Analyst is not — the same title is used for 0-YOE and 10-YOE roles. So Stage 1 only fires on explicit level markers and a short list of role nouns that are only ever entry-level; everything else is deliberately left ambiguous for Stages 2–3.

Interaction with the exclude pre-filter (§5.2): by the time a title reaches Stage 1, explicitly-senior titles ("Senior…", "…Manager", "Lead…") are already gone. Stage 1 therefore only has to separate intern vs. entry vs. still-ambiguous, not fight off senior roles.

A · INTERNSHIP — high confidence (checked first)

Regex (case-insensitive, on title)Matches
\b(intern|internship)\b"Supply Chain Intern", "Procurement Internship" — \b avoids "internal"/"international"
\bco[-\s]?op\b"Logistics Co-op", "Supply Chain Coop"
\bsummer\s+(analyst|associate|scholar)\b"Summer Analyst" (bank/CPG intern convention)
\b(DCM|MBA)\s+intern / intern\b.*\b20\d{2}\b"DCM Internship", "Supply Chain Intern – Summer 2026"

B · ENTRY_LEVEL — explicit level markers, high confidence

RegexMatches
\b(new|recent|university|college)\s+grad(uate)?\b"New Grad", "University Graduate", "Recent Graduate"
\bentry[-\s]?level\b"Entry-Level Buyer"
\b(jr\.?|junior)\b"Junior Planner", "Jr. Buyer"
\b(analyst|coordinator|specialist|planner|buyer|associate)\s*(I|1)\b"Supply Chain Analyst I", "Buyer 1" (but not "II"/"2")
\b(rotational|leadership\s+development|management\s+trainee|(early\s+career\s+)?development)\s+program\b"Supply Chain Rotational Development Program", "Leadership Development Program", "Management Trainee Program"
\b(campus|early\s+career|trainee)\b"Campus Hire", "Early Career Sourcing", "Procurement Trainee"

C · ENTRY_LEVEL — entry-only role nouns, medium confidence

These role nouns are, in practice, never used for senior SCM roles (a senior person is a "Manager"/"Lead", already excluded). Treated as ENTRY_LEVEL when no seniority marker survived §5.2:

\b(coordinator|assistant|administrator)\b   →  ENTRY_LEVEL
   e.g. Logistics Coordinator, Purchasing Assistant, Warehouse Administrator,
        Procurement Coordinator, Buyer's Assistant, Sourcing Assistant

D · Ambiguous role nouns — do not auto-classify (→ null → Stage 2)

These titles span the full seniority range with no marker, so Stage 1 must pass them down for YOE / Gemini judgment. This is the main behavioral change from SWE's title stage:

Supply Chain Analyst · Logistics Analyst · Operations Analyst
Procurement / Sourcing Specialist · Buyer · Demand / Supply Planner
Inventory Analyst · Category Analyst
   → no level word → return null → Stage 2 (description YOE) → Stage 3 (Gemini)

Precedence

  1. A (INTERNSHIP) wins over everything — an explicit "intern" token beats any entry marker (e.g. "Supply Chain Intern — New Grad Program" → INTERNSHIP).
  2. then B (explicit entry marker) → ENTRY_LEVEL;
  3. then C (entry-only role noun) → ENTRY_LEVEL;
  4. else D → null (defer).

Stage 2 — Description signals (SignalExtractor.inferLevelFromDescription) — local, no API

  • Internship signals → INTERNSHIP: "currently enrolled", "pursuing a [Bachelor/Master] degree", "rising junior/senior", "expected graduation", "current student", "must be enrolled". Checked first — enrollment beats YOE.
  • YOE parsing (reuse YOE_PATTERN, per Decision D4: entry = 0–3 YOE): > 3 years → OTHER (too senior); 0–3 years with no internship signal → ENTRY_LEVEL.
  • Entry keywords in the JD are extracted as Signal records for the Gemini prompt but — as in SWE — not used to auto-classify, to avoid false positives ("graduate" = degree requirement, "university" = campus location).
  • Returns null → Stage 3.

Stage 3 — Gemini 2.5 Flash (JobClassifier + GeminiClient) — batched

  • Remaining ambiguous jobs batched (50/call) and sent to Gemini for a 4-way classification: ENTRY_LEVEL / INTERNSHIP / UNSURE / OTHER. Gemini returns UNSURE when a role is clearly early-career but the description won't commit to intern vs. full-time.
  • Prompt includes title, company, and the structured Signal snippets from Stage 2. Prompt text is rewritten for the SCM entry-vs-intern question (the only prompt-level change from SWE).
  • Output written to level.

Retry & fallback — unchanged mechanism

Gemini failures increment classificationFailures; retried on later polls; after 3 failures the job is auto-approved rather than silently dropped.

Decision D3 (resolved): the fallback label is UNSURE. A posting that exhausts its 3 Gemini attempts still gets emailed (UNSURE rows are notified), just flagged as unclassified — so nothing is silently dropped and no guess is forced onto the entry/intern split.

7. Notification & Routing

Independent 5-minute scanner (NotificationService), same cadence as SWE, but one email to one recipient list instead of two per-track emails (Decision D1). Each scan collects every unnotified posting whose level is ENTRY_LEVEL, INTERNSHIP, or UNSURE, renders them as rows in a single table with a Type column, sends one message, then marks them notified. 

candidates = level IN (ENTRY_LEVEL, INTERNSHIP, UNSURE) AND notified = false
if candidates not empty:
    render ONE table, one row per job, Type column = the level label
    send ONE email  →  job.notification.to        (single recipient list)
    on success → notified = true   |   on failure → retry next scan
OTHER  →  never emailed

12. Resolved Design Decisions

All four are settled (2026-08-09) and reflected throughout the doc above.

D1 — Notification structure → single email, single list.
One alert email to one recipient list (job.notification.to). ENTRY_LEVEL, INTERNSHIP, and UNSURE postings appear as rows in one table with a Type column. The two-list SWE model is dropped. (See §7.)
D2 — Remote roles → CA-tokened only.
Accept "Remote" only when the location also carries a CA / California token. Bare "Remote - US" is dropped for now. (See §5.3.)
D3 — Gemini fallback → UNSURE.
After 3 failed Gemini attempts a posting is labeled UNSURE (still emailed, flagged unclassified), not forced into entry or intern. (See §6 Retry & Fallback.)
D4 — Entry-level band → 0–3 YOE.
Stage 2: 0–3 years (no intern signal) → ENTRY_LEVEL; > 3 years → OTHER. (See §6 Stage 2.)

Remaining before implementation: finalize the target-employer list (§8) and their ATS mappings; that's the only open input left.
